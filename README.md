# Handys Stay Operations Dashboard

호텔 운영자가 객실, 청소 작업, 운영 이슈를 하나의 흐름으로 관리하는 내부 운영 대시보드입니다. 첫 화면의 목표는 상세 데이터를 많이 보여주는 것이 아니라, 출근한 운영자가 **“지금 가장 먼저 처리할 일이 무엇인가?”**를 바로 판단하게 하는 것입니다.

## 문제 정의

체크아웃 이후 객실은 청소 배정, 진행, 검수를 거쳐 다음 게스트를 맞을 준비가 됩니다. 이 과정에서 청소와 시설 이슈를 서로 다른 화면에서 따로 확인하면 체크인 임박 객실이나 판매 중지 객실을 늦게 발견하기 쉽습니다.

이 프로젝트는 세 가지 질문에 각각 하나의 화면으로 답합니다.

| 화면 | 답해야 하는 질문 | 화면의 기준 |
| --- | --- | --- |
| 대시보드 | 오늘 무엇부터 해야 하는가? | 통합 우선순위 |
| 객실 현황 | 이 객실을 지금 운영할 수 있는가? | 객실 |
| 청소 작업 | 청소가 어디까지 진행됐는가? | 작업 |
| 운영 이슈 | 해결해야 할 문제가 무엇인가? | 이슈 |

## 핵심 운영 흐름

```text
예약 → 체크아웃 → 청소 필요 → 크루 배정 → 청소 중 → 검수 대기 → 입실 가능 → 체크인 → 투숙 중
```

시설 문제가 생기면 객실을 판매 중지하고, 조치와 필요 시 재청소를 거쳐 다시 입실 가능 상태로 전환합니다.

```text
운영 이슈 → 판매 중지 → 조치 → 재청소(필요 시) → 입실 가능
```

## 제품 설계 원칙

### 1. 객실 상태와 청소 상태를 분리

객실 상태는 운영 가능 여부만 표현합니다.

- 투숙 중
- 입실 가능
- 입실 예정
- 청소 필요
- 판매 중지

`배정 완료`, `청소 중`, `검수 대기`는 객실 상태가 아니라 청소 작업의 진행 단계입니다. 청소가 완료되기 전까지 객실 상태는 일관되게 `청소 필요`로 유지하고, 상세 진행 단계는 청소 작업 화면에서 보여줍니다.

### 2. 긴급 작업을 하나의 큐로 통합

대시보드는 청소와 운영 이슈를 따로 잘라 합치지 않습니다. 모든 미완료 작업을 아래 순서로 한 번 정렬한 뒤 Top 4만 보여줍니다.

1. 체크인 60분 이내 + 청소 미완료
2. 긴급 운영 이슈
3. 청소 버퍼 초과
4. 검수 대기
5. 일반 작업

청소 버퍼는 `다음 체크인까지 남은 시간 - 남은 예상 청소 시간`으로 계산합니다. 청소 중인 작업은 이미 경과한 시간을 예상 소요 시간에서 차감합니다.

### 3. 대시보드는 요약, 상세 화면은 실행

대시보드의 객실·청소·이슈 섹션은 각각 Top 5만 노출합니다. 담당자 배정, 상태 변경, 검수, 이슈 처리 같은 실제 작업은 각 상세 화면에서 수행합니다.

### 4. MVP 밖의 메뉴도 정보 구조에는 표시

예약 관리, 크루 관리, 숙소 관리, 메시지, 리포트, 설정은 전체 제품의 정보 구조를 보여주되 `SOON` 상태로 명확히 구분했습니다. 동작하지 않는 버튼처럼 보이지 않도록 비활성 메뉴로 처리했습니다.

## 구현 범위

### 포함

- 지역·지점 필터가 적용되는 오늘의 운영 KPI
- 청소와 운영 이슈를 통합한 긴급 작업 Top 4
- 배정 판단을 돕는 오늘의 크루 업무량·대기 현황
- 우선순위 기반 객실 현황, 청소 작업, 운영 이슈 목록
- 객실 상세: 예약 정보, 도어락, 청소 기록, 이슈 기록
- 청소 상세: 크루 추천·배정·재배정, 진행 상태 변경, 운영자 검수, 재청소
- 운영 이슈 등록·상세: 담당자 배정, 객실 판매 중지·재개, 상태 변경, 처리 대화
- 이슈 내용 기반 카테고리·긴급도 추천(운영자가 최종 결정)
- 데스크톱 사이드바와 모바일 하단 내비게이션

### 의도적으로 제외

- 실제 OTA 예약, 결제, 도어락 시스템 연동
- 게스트용 앱과 실시간 메시징
- 로그인 및 역할별 권한 관리
- 사진 영구 저장소 연동(검수 흐름을 위한 로컬 미리보기만 제공)
- 크루 위치, 숙련도, 재청소율 등을 반영한 복합 추천

추천 로직은 현재 배정 작업 수라는 설명 가능한 한 가지 기준만 사용합니다. 검증되지 않은 가중치를 늘려 추천의 근거가 불투명해지는 것을 피했습니다.

## 사용자와 이슈 접수 흐름

주 사용자는 숙소 오너나 투숙객이 아닌 핸디즈 내부 운영 담당자입니다. 게스트가 전화, 프론트, OTA 메시지로 알린 내용을 운영자가 대리 입력하고 현장 크루 또는 시설 담당자에게 연결합니다.

```text
Guest → 전화 / 프론트 / OTA → Handys Operations → Cleaning Crew / Facility Partner
```

## 기술 구성

- Next.js 16 App Router, React 19, TypeScript
- Tailwind CSS 4
- Supabase(Postgres)
- React Server Components에서 조회, Route Handler에서 상태 변경과 전이 검증
- Supabase Service Role Key는 서버 모듈에서만 사용하고 클라이언트 번들에 노출하지 않음

주요 판단 로직은 다음 파일에 분리했습니다.

- `src/lib/roomDisplayStatus.ts`: 객실 운영 상태 계산 및 정렬 순서
- `src/lib/priority.ts`: 체크인 버퍼와 청소 지연 위험 계산
- `src/lib/transitions.ts`: 청소·이슈 상태 전이 규칙
- `src/lib/queries.ts`: 화면별 조회, 상세 목록 및 통합 작업 우선순위

## 실행 방법

Next.js 16 요구사항에 맞춰 Node.js 20.9 이상이 필요합니다. `.nvmrc`가 포함되어 있습니다.

```bash
nvm use
npm install
cp .env.local.example .env.local
```

Supabase SQL Editor에서 `supabase/schema.sql`, `supabase/seed.sql` 순서로 실행하고 `.env.local`에 Supabase URL과 Service Role Key를 입력합니다. 시드의 시간은 실행 시점 `now()`를 기준으로 생성되므로 긴급·지연 시나리오를 바로 확인할 수 있습니다.

```bash
npm run dev
```

이슈 자동 분류를 사용하려면 `ANTHROPIC_API_KEY`를 추가합니다. 키가 없어도 나머지 기능은 정상 동작합니다.

## 확장 시 고려사항

현재 지역과 지점 매핑은 과제 범위에서 `src/lib/regions.ts`에 정적으로 정의했습니다. 실제 서비스에서는 `regions → branches → rooms` 테이블로 정규화해야 지점 추가와 이전을 배포 없이 처리할 수 있습니다.

또한 현재 `rooms.branch`는 문자열이지만 운영 규모가 커지면 `branch_id` FK로 변경하고, 예약은 별도 `reservations` 테이블로 분리해 객실의 현재 투숙 정보와 다음 예약을 계산하는 구조가 적합합니다.
