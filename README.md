# Stay Operations Dashboard

객실(Room) 상태를 중심으로 청소 업무와 객실 이상 신고를 하나의 흐름으로 관리하는 숙박 운영 대시보드입니다.

## 문제 정의

숙박 시설은 매일 체크인·체크아웃 객실 수가 달라지고, 그에 따라 청소량과 점검 업무도 계속 바뀝니다. 운영자는 아래 정보를 반복적으로 확인해야 합니다.

- 오늘 체크아웃한 객실 / 청소가 필요한 객실
- 청소 담당자가 아직 배정되지 않은 객실
- 다음 체크인까지 시간이 부족한 객실 (지연 위험)
- 청소는 끝났지만 검수가 필요한 객실
- 시설 이상이나 청소 불량이 신고된 객실과 처리 담당자

이 정보들이 여러 화면과 수기 업무로 나뉘어 있으면 운영자는 문제를 늦게 발견하거나 같은 내용을 반복해서 확인하게 됩니다. 특히 다음 체크인 전까지 청소나 시설 문제를 해결하지 못하면 고객 경험 저하와 객실 판매 손실로 이어집니다.

## 해결 방향

예약·청소·이상 신고가 각각 분리되어 관리되면서 발생하는 운영 병목을 줄이기 위해, **객실 상태를 중심으로 청소 배정과 이상 신고를 연결한 운영 대시보드**를 설계했습니다. 운영자는 메인 화면에서 지금 처리해야 할 업무를 우선순위 순으로 확인할 수 있습니다.

### 객실 상태 전이

```
Occupied → Dirty → Assigned → Cleaning → Inspection → Ready
                                   ↓
                                 Issue → (처리 완료 후) Inspection → Ready
```

## 사용자 정의 및 이슈 접수 흐름

핸디즈는 오너를 대신해 숙소를 위탁운영하는 구조이므로, 이 대시보드의 "운영자"는 오너나 투숙객이 아니라 **핸디즈 내부 운영 담당자**입니다. 오너·투숙객이 직접 보는 화면이 아니라, 위탁운영을 대행하는 핸디즈 팀이 청소·이슈 처리를 관리하는 내부 콘솔입니다.

투숙객이 문제를 알리는 경로는 전화, 프론트 데스크 응대, OTA 메시지 등 기존 채널을 그대로 쓰고, 그 내용을 운영자가 시스템에 대리 입력합니다.

```
Guest → (전화 / 프론트 / OTA 메시지) → Operations(핸디즈) → Cleaning Crew / Facility Partner
```

이슈 등록 화면의 "신고자" 항목(투숙객/청소 담당자/운영자/시설 담당자)이 이 대리 입력 구조를 반영합니다. 투숙객 전용 앱이나 실시간 채팅을 별도로 만들지 않고, 콜센터가 고객 문의를 CRM에 대신 기록하는 방식과 동일하게 접근했습니다.

## MVP 범위

과제 특성상 전체 흐름을 다 구현하지 않고, 운영자의 판단을 가장 많이 줄여주는 지점 위주로 범위를 좁혔습니다.

### 포함

1. **운영 대시보드** — 오늘 체크인/체크아웃, 청소 필요·미배정 객실, 지연 위험 객실, 이슈 현황을 우선순위 순으로 표시
2. **청소 작업 리스트 및 상태 변경** — 담당자 배정, 진행 상태 변경, 배정 추천(현재 배정 작업 수가 가장 적은 담당자 추천)
3. **객실 이상 신고 등록/상세/담당자 배정** — 신고 유형·긴급도 분류, 담당자 배정, 처리 상태 변경

### 제외 (의도적으로 뺀 범위)

- 투숙객 전용 신고 앱/실시간 채팅 (위 "이슈 접수 흐름" 참고 — 대리 입력 구조로 대체), 사진 업로드, 다국어 번역, 실제 로그인/권한 관리
- 지역 기반 청소 크루 배정(다인 마켓플레이스 구조) — 개념은 유효하지만 이번 범위에서는 화면으로 구현하지 않음
- 배정 추천에 쓸 수 있는 기준(근무 가능 여부, 숙련도, 재청소율 등)은 여러 가지가 있지만, 이번 MVP에서는 "현재 배정 작업 수" 한 가지 기준만 사용했습니다. 기준이 늘어날수록 검증되지 않은 가중치가 늘어나 오히려 신뢰하기 어려운 추천이 될 수 있다고 판단했습니다.

실제 예약 생성/취소, OTA 연동, 도어락 연동, 결제, 정산은 구현 범위에서 제외하고 Mock Data 또는 Supabase에 저장된 시나리오 데이터로 대체합니다.

## 우선순위(지연 위험) 로직

객실별로 "다음 체크인까지 남은 시간 − 예상 청소 소요 시간"을 여유 시간으로 계산하고, 여유 시간이 짧은 순으로 대시보드에 정렬합니다. 여유 시간이 음수이거나 임계값 이하인 객실은 지연 위험으로 표시되며, 미배정 상태인 경우 우선순위를 한 단계 더 올립니다.

## 아키텍처

- **Frontend**: Next.js (App Router), TypeScript, Tailwind CSS
- **API**: Next.js Route Handler로 자체 API 레이어(`/api/rooms`, `/api/cleaning-tasks`, `/api/issues`)를 두고, 상태 전이 검증·지연 위험 계산·배정 추천 같은 판단 로직을 서버에서 처리합니다. 프론트는 이 API 응답을 그대로 렌더링합니다.
- **Database**: Supabase(Postgres) — rooms / cleaning_tasks / issues 테이블로 도메인을 모델링하고, 클라이언트에는 테이블을 직접 노출하지 않습니다.

### 지역/지점 구조 (샘플)

핸디즈는 여러 지점을 각각 다른 호텔 브랜드로 위탁운영하는 구조이므로, `rooms.branch`에는 지점별 실제 호텔명이 들어갑니다(예: "노블리안 강남", "강남 스퀘어 스테이"). 헤더의 지역 선택은 서울 강남구·서울 마포구·부산 해운대구 3개 구를 샘플로 구현했고, 구 하나에 지점(호텔) 2곳씩을 매핑해 지역 → 지점 드릴다운을 보여줍니다. 이 매핑은 `src/lib/regions.ts`에 정적 데이터로 하드코딩되어 있습니다.

실제 서비스로 확장한다면 이 매핑은 코드가 아니라 DB 스키마로 옮겨야 합니다. `regions`(구/시 단위) → `branches`(지점, region_id FK + 호텔명) → `rooms`(branch_id FK)로 정규화하면, 지점 추가/이전이 배포 없이 데이터 등록만으로 가능해지고 지역별 집계도 SQL 조인으로 처리할 수 있습니다.

## AI 활용 및 검토 원칙

객실 이상 신고 등록 시, 입력된 신고 내용을 바탕으로 신고 유형과 긴급도를 추천합니다. AI 결과는 최종 값이 아니라 추천값으로만 사용하며, 원문과 AI 추천 결과를 함께 보여주고 운영자가 최종 분류·긴급도를 직접 수정할 수 있도록 구성합니다.

## 실행 방법

1. Supabase 프로젝트를 생성하고, SQL Editor에서 `supabase/schema.sql` → `supabase/seed.sql` 순서로 실행합니다.
2. `.env.local.example`을 `.env.local`로 복사하고 Supabase 프로젝트의 URL/서비스 롤 키를 채웁니다. 이슈 자동 분류 기능을 쓰려면 `ANTHROPIC_API_KEY`도 채웁니다 (없어도 나머지 기능은 정상 동작합니다).
3. 아래 명령으로 실행합니다.

```bash
npm install
npm run dev
```
